Venice-API-Anfragen werden mit Bearer-API-Schlüsseln authentifiziert. Diese Anleitung zeigt, wie Sie einen Schlüssel über das Venice-Dashboard erstellen, sicher aufbewahren und seine Funktion überprüfen.

<Note>
  Wenn Sie einen autonomen Agenten entwickeln, der seinen eigenen Schlüssel mit einer Wallet erstellen muss, verwenden Sie stattdessen die Anleitung [Erstellung von API-Schlüsseln für autonome Agenten](/guides/integrations/generating-api-key-agent).
</Note>

## Bevor Sie beginnen {#before-you-start}

* Melden Sie sich bei Ihrem Venice-Konto an.
* Stellen Sie sicher, dass das Konto über ein verfügbares Guthaben verfügt, bevor Sie kostenpflichtige Endpunkte aufrufen. Sie können einen Schlüssel erstellen, bevor Sie das Konto aufladen, aber Modellanfragen sind erst dann erfolgreich, wenn das Konto DIEM, gebündelte Credits oder USD verbrauchen kann.

<Steps>
  <Step title="API-Einstellungen öffnen">
    Rufen Sie [https://venice.ai/settings/api](https://venice.ai/settings/api?utm_source=venice-api-documentation) auf. Sie können diese Seite auch in der Venice-App öffnen, indem Sie in Ihren Einstellungen **API** auswählen.

    Das API-Einstellungs-Dashboard zeigt Ihre Guthaben, Ihre API-Stufe, die Nutzung und vorhandene API-Schlüssel an.
  </Step>

  <Step title="Neuen Schlüssel starten">
    Wählen Sie **Generate New API Key** und konfigurieren Sie anschließend den Schlüssel:

    * **Description:** Verwenden Sie einen kurzen Namen, der die App, die Umgebung oder die Integration identifiziert, die diesen Schlüssel verwenden wird.
    * **API Key Type:** Verwenden Sie **Inference Only** für normale Modellanfragen. Verwenden Sie **Admin** nur dann, wenn der Schlüssel API-Schlüssel programmgesteuert verwalten soll.
    * **Expires at:** Legen Sie optional ein Ablaufdatum fest. Wenn Sie dieses Feld leer lassen, läuft der Schlüssel nicht automatisch ab.
    * **Epoch Consumption Limits:** Begrenzen Sie optional, wie viel DIEM oder USD dieser Schlüssel innerhalb einer 24-Stunden-Epoche ausgeben darf. Wenn Sie dieses Feld leer lassen, kann der Schlüssel das verfügbare Kontoguthaben im Rahmen Ihrer Kontolimits nutzen.
  </Step>

  <Step title="Schlüssel generieren und kopieren">
    Klicken Sie auf **Generate**. Venice zeigt den vollständigen API-Schlüssel einmalig an.

    <Warning>
      Kopieren Sie den Schlüssel sofort und bewahren Sie ihn an einem sicheren Ort auf. Nachdem Sie den Dialog geschlossen haben, zeigt Venice nur noch identifizierende Metadaten wie die Schlüsselbeschreibung und die letzten Zeichen an. Wenn Sie den geheimen Wert verlieren, löschen Sie den Schlüssel und erstellen Sie einen neuen.
    </Warning>

    Fügen Sie den Schlüssel genau so ein, wie er ausgegeben wurde. Verwenden Sie die Kopierschaltfläche des Dialogs, statt den Text von Hand zu markieren, damit Sie weder das erste noch das letzte Zeichen abschneiden oder einen abschließenden Zeilenumbruch mitkopieren. Wenn ein Tool den Schlüssel in einem Formularfeld abfragt, geben Sie nur den Schlüssel selbst ein: kein `Bearer`-Präfix, keine umschließenden Anführungszeichen und keine führenden oder abschließenden Leerzeichen. Da das Dashboard nach dem Schließen des Dialogs nur noch die letzten Zeichen anzeigt, sollten Sie niemals versuchen, einen verlorenen Schlüssel durch Abtippen dieses maskierten Werts zu rekonstruieren.

    Fügen Sie den Schlüssel zu Ihrer lokalen Umgebung oder Ihrem Secret-Manager hinzu:

    ```bash
    export VENICE_API_KEY=your-api-key-here
    ```
  </Step>

  <Step title="Schlüssel verifizieren">
    Stellen Sie eine risikoarme Anfrage, um zu bestätigen, dass die Authentifizierung funktioniert. [Ratenlimits und Guthaben eines API-Schlüssels abrufen](/de/api-reference/endpoint/api_keys/rate_limits) ist kostenlos und akzeptiert beide Schlüsseltypen. Verwenden Sie diesen Endpunkt statt `GET /models`, der den Modellkatalog mit oder ohne Schlüssel zurückgibt und daher auch dann erfolgreich ist, wenn Ihr Schlüssel falsch ist:

    ```bash
    curl --request GET \
      --url https://api.venice.ai/api/v1/api_keys/rate_limits \
      --header "Authorization: Bearer $VENICE_API_KEY"
    ```

    Eine erfolgreiche Antwort liefert Ihre API-Stufe, Ihre Guthaben und Ihre Ratenlimits zurück, und `data.accessPermitted` gibt an, ob der Schlüssel die Inferenz-Endpunkte nutzen darf.

    Ein `401` mit `AUTHENTICATION_FAILED` bedeutet, dass der Schlüssel selbst abgelehnt wurde. Geben Sie den gespeicherten Wert aus und vergleichen Sie ihn mit den letzten Zeichen, die im Dashboard angezeigt werden: Die üblichen Ursachen sind eine unvollständige Kopie, ein `Bearer`-Präfix oder Anführungszeichen, die in den Wert selbst übernommen wurden, oder ein überzähliges Leerzeichen bzw. ein Zeilenumbruch an einem der beiden Enden. Prüfen Sie außerdem, ob der Header aus `Bearer`, einem Leerzeichen und dann dem Schlüssel selbst besteht, zum Beispiel `Authorization: Bearer $VENICE_API_KEY` in einer Shell.
  </Step>
</Steps>

<Warning>
  Wenn Sie beim Erstellen eines API-Schlüssels in der Venice-App die USD-Ausgaben deaktivieren, wird das USD-Ausgabenlimit für den betreffenden API-Schlüssel auf null gesetzt. API-Aufrufe können mit einem Fehler wegen unzureichenden Guthabens fehlschlagen, wenn Ihr verfügbares DIEM- oder gebündeltes Guthaben die Anfrage nicht decken kann – selbst wenn Ihr Konto ein USD-Guthaben hat.
</Warning>

## Schlüsselformat {#key-format}

Neue Schlüssel beginnen mit einem Typpräfix, gefolgt von 42 URL-sicheren Zeichen:

| Präfix | Schlüsseltyp |
| --- | --- |
| `VENICE_INFERENCE_KEY_` | Inference Only |
| `VENICE_ADMIN_KEY_` | Admin |

Ältere Schlüssel funktionieren weiterhin so, wie sie ausgestellt wurden: Einige verwenden Bindestriche im Präfix (`VENICE-INFERENCE-KEY-`, `VENICE-ADMIN-KEY-`), und die ältesten haben gar kein Präfix.

Verwenden Sie den Schlüssel genau so, wie er ausgestellt wurde. Die API prüft die gesamte Zeichenfolge. Ein Schlüssel, den ein Tool in Kleinbuchstaben umgewandelt, anders interpunktiert, um sein Präfix gekürzt oder mit einem anderen Präfix versehen hat, schlägt daher mit `401` und `Authentication failed` fehl. Einige Community-Seiten behaupten, Venice-Schlüssel begännen mit `vapi_`. Das stimmt nicht, und wenn Sie einem Schlüssel `vapi_` hinzufügen, funktioniert er nicht mehr.

Das Präfix kennzeichnet den Schlüsseltyp. Ein Admin-Schlüssel funktioniert auch an Modell-Endpunkten, weil er der umfassendere Typ ist. Ein **Inference Only**-Schlüssel an einem Admin-Endpunkt, etwa zum Auflisten oder Erstellen von Schlüsseln oder zum Abrufen des Guthabens, schlägt mit `401` und `Admin API key required` fehl. `GET /api_keys/rate_limits` akzeptiert beide Typen.

## Fehlerbehebung bei Ausgabenlimit-Fehlern {#troubleshooting-spend-limit-errors}

Ausgabenlimits pro Schlüssel sind vom Guthaben Ihres Kontos getrennt. Ein Schlüssel kann von Ausgaben ausgeschlossen sein, selbst wenn Ihr Konto noch über aufgeladene USD-Credits, DIEM oder gebündelte Credits verfügt. Wenn eine Anfrage einen 402-Fehler mit einem der folgenden Codes zurückgibt, liegt die Ursache im Limit des Schlüssels selbst und nicht am Kontoguthaben:

* `API_KEY_USD_SPEND_LIMIT_EXCEEDED` – Das USD-Ausgabenlimit des Schlüssels ist auf null gesetzt (USD-Ausgaben wurden bei der Erstellung deaktiviert), oder die aktuelle Epoche hat ihre USD-Obergrenze erreicht.
* `API_KEY_DIEM_SPEND_LIMIT_EXCEEDED` – Der Schlüssel hat seine DIEM-Obergrenze für die aktuelle 24-Stunden-Epoche erreicht.

Um den aktuellen Status eines Schlüssels zu überprüfen, rufen Sie [Ratenlimits und Guthaben eines API-Schlüssels abrufen](/de/api-reference/endpoint/api_keys/rate_limits) auf und prüfen Sie `data.accessPermitted` und `data.balances`. Um die konfigurierten Limits des Schlüssels einzusehen, rufen Sie [API-Schlüssel abrufen](/de/api-reference/endpoint/api_keys/get) mit einem Admin-Schlüssel auf und lesen Sie `consumptionLimits` aus.

Um den Fehler zu beheben, erhöhen oder entfernen Sie entweder die Epoch Consumption Limits des Schlüssels unter [venice.ai/settings/api](https://venice.ai/settings/api?utm_source=venice-api-documentation), oder rufen Sie [API-Schlüssel aktualisieren](/de/api-reference/endpoint/api_keys/update) mit einem neuen `consumptionLimit`-Objekt auf. Das Request-Feld steht im Singular, obwohl die Antworten zu API-Schlüsseln `consumptionLimits` zurückgeben. Kontoweite Guthaben (USD, DIEM und gebündelte Credits) sind unabhängige Zahlungsquellen und werden automatisch nach Verfügbarkeit verbraucht; Sie müssen zum Zeitpunkt der Anfrage keine Auswahl treffen.

Siehe [Fehlercodes](/api-reference/error-codes) für die vollständige Liste der abrechnungsbezogenen Antworten.

## Best Practices {#best-practices}

* Erstellen Sie separate Schlüssel für Entwicklung, Staging und Produktion.
* Bevorzugen Sie **Inference Only**-Schlüssel für Anwendungen, die ausschließlich Modell-Endpunkte aufrufen.
* Setzen Sie **Admin**-Schlüssel nur selten ein, beschränken Sie ihren Geltungsbereich strikt und speichern Sie sie ausschließlich in vertrauenswürdigen serverseitigen Umgebungen.
* Speichern Sie API-Schlüssel niemals in der Versionskontrolle und geben Sie sie niemals in clientseitigem Code preis.
* Legen Sie Ablaufdaten und Verbrauchslimits für Schlüssel fest, die in temporären, gemeinsam genutzten oder risikoreicheren Umgebungen verwendet werden.
* Löschen Sie ungenutzte Schlüssel und rotieren Sie jeden Schlüssel, der möglicherweise offengelegt wurde.

## Aufrufe aus dem Browser {#calling-from-a-browser}

Die API sendet `access-control-allow-origin: *`, daher kann ein Browser sie direkt aufrufen. Dann steckt der Schlüssel jedoch in Ihrem Bundle und ist öffentlich. Schalten Sie einen kleinen Proxy davor und behalten Sie den Schlüssel auf dem Server.

Ein Proxy allein reicht nicht. `access-control-allow-origin` authentifiziert nichts: `curl` und andere Server ignorieren CORS vollständig, und der Hostname des Workers ist öffentlich. Ein Proxy, der nur den Schlüssel einfügt, ist ein offener Hahn für Ihr Guthaben. Auch der Aufrufer muss sich ausweisen.

Es gibt zwei Stufen, und es ist wichtig, welche Sie bauen:

- **Ein gemeinsames Geheimnis** schützt die Ausgaben. Jeder Besucher hat denselben Wert. Es verhindert also die anonyme Nutzung Ihres Workers, aber nicht, dass ein Besucher ihn weitergibt. Gut für einen Prototyp.
- **Ein Token pro Benutzer** identifiziert den Aufrufer. Der Browser authentifiziert sich bei Ihrem eigenen Backend, das ein kurzlebiges Token ausstellt, und der Worker validiert es. Das ist die Form für die Produktion.

Beide Beispiele unten behalten den Venice-Schlüssel auf dem Server. Für beide gilt eine dritte Regel: **Verwenden Sie einen Inference-Only-Schlüssel**, denn ein Admin-Schlüssel, der über einen öffentlichen Proxy läuft, kann `POST /api_keys` aufrufen und das neue Secret direkt aus der weitergeleiteten Antwort auslesen.

### Stufe 1: ein gemeinsames Geheimnis {#level-1-a-shared-secret}

Der Worker hält den Venice-Schlüssel und ein Geheimnis und lehnt alles ohne dieses Geheimnis ab. Halten Sie das Geheimnis vom Browser fern: Lassen Sie Ihr Backend es anhängen, wenn es den Worker aufruft, sodass der Browser nur mit Ihrem Backend spricht.

```js index.js
// Only the paths you need. Add deliberately: an inference key still reads
// balances through GET /api_keys/rate_limits.
const ALLOWED = new Set(['/chat/completions', '/image/generate']);

export default {
  async fetch(request, env) {
    if (request.method === 'OPTIONS') {
      return new Response(null, { headers: cors() });
    }
    if (!ALLOWED.has(new URL(request.url).pathname)) {
      return json(404, { error: 'Not found' });
    }
    if (request.method !== 'POST') {
      return json(405, { error: 'Method not allowed' });
    }
    if (request.headers.get('x-proxy-key') !== env.PROXY_SECRET) {
      return json(401, { error: 'Proxy secret required' });
    }
    return forward(request, env);
  },
};

async function forward(request, env) {
  const path = new URL(request.url).pathname;
  const upstream = await fetch(`${env.VENICE_BASE_URL}/api/v1${path}`, {
    method: 'POST',
    headers: { 'content-type': 'application/json', authorization: `Bearer ${env.VENICE_API_KEY}` },
    body: await request.text(),
  });
  return new Response(upstream.body, {
    status: upstream.status,
    headers: { ...cors(), 'content-type': upstream.headers.get('content-type') ?? 'application/json' },
  });
}

const cors = () => ({
  'access-control-allow-origin': 'https://your-site.example',
  'access-control-allow-headers': 'content-type,x-proxy-key',
  'access-control-allow-methods': 'POST,OPTIONS',
});

const json = (status, body) =>
  new Response(JSON.stringify(body), { status, headers: { ...cors(), 'content-type': 'application/json' } });
```

```bash Deploy
npx wrangler deploy index.js --name venice-proxy
npx wrangler secret put VENICE_API_KEY      # an inference-only key
npx wrangler secret put PROXY_SECRET        # any long random value
npx wrangler secret put VENICE_BASE_URL     # https://api.venice.ai
```

Rufen Sie ihn aus Ihrem Backend auf, wo das Geheimnis bleibt:

```js Server
await fetch('https://venice-proxy.<account>.workers.dev/chat/completions', {
  method: 'POST',
  headers: { 'content-type': 'application/json', 'x-proxy-key': process.env.PROXY_SECRET },
  body: JSON.stringify({ model: 'venice-uncensored-1-2', messages: [{ role: 'user', content: 'Hi' }] }),
});
```

Pfade werden direkt angehängt, daher erreicht `/chat/completions` upstream `/api/v1/chat/completions`. Lassen Sie `/v1` in der Basis-URL jedes OpenAI-Clients weg, den Sie hierauf richten.

Ein gemeinsames Geheimnis bleibt eine gemeinsam genutzte Zugangsberechtigung: Begrenzen Sie die Rate der Route mit den Rate-Limiting-Regeln von Cloudflare, bevor sie öffentlichen Traffic erhält.

### Stufe 2: ein Token pro Benutzer {#level-2-a-per-user-token}

Wenn der Browser den Worker direkt aufrufen muss, setzen Sie Ihre eigene Authentifizierung davor. Ihr Backend prüft die Sitzung, die es bereits hat, und signiert ein kurzlebiges Token. Der Worker prüft dieses Token statt eines gemeinsamen Werts. Er verwendet `ALLOWED`, `forward`, `cors` und `json` aus dem Worker der Stufe 1 wieder:

```js index.js
export default {
  async fetch(request, env) {
    if (request.method === 'OPTIONS') {
      return new Response(null, { headers: cors() });
    }
    if (!ALLOWED.has(new URL(request.url).pathname) || request.method !== 'POST') {
      return json(404, { error: 'Not found' });
    }
    if (!(await validToken(request.headers.get('authorization')?.replace(/^Bearer /, ''), env))) {
      return json(401, { error: 'Token required' });
    }
    return forward(request, env);
  },
};

// Verify a token issued by your backend: its signature, expiry and subject.
// Any HMAC over `sub.exp` works; this is the shape, not a full implementation.
async function validToken(token, env) {
  if (!token) return false;
  // The payload itself contains a dot, so split on the last one only.
  const cut = token.lastIndexOf('.');
  if (cut < 1) return false;
  const payload = token.slice(0, cut);
  const key = await crypto.subtle.importKey(
    'raw', new TextEncoder().encode(env.PROXY_SIGNING_KEY),
    { name: 'HMAC', hash: 'SHA-256' }, false, ['verify'],
  );
  const ok = await crypto.subtle.verify('HMAC', key, hexToBytes(token.slice(cut + 1)), new TextEncoder().encode(payload));
  return ok && Number(payload.slice(payload.lastIndexOf('.') + 1)) > Date.now();
}

const hexToBytes = (hex) => new Uint8Array(hex.match(/../g).map((b) => parseInt(b, 16)));
```

Stellen Sie das Token im Backend nach Ihrer eigenen Sitzungsprüfung aus, damit der Worker nie Benutzerzustand hält. So erhalten Sie Rate Limits pro Benutzer, Widerruf und eine zuordenbare Abrechnung.
