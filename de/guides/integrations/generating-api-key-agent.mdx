'og:description': Wie ein autonomer KI-Agent seinen eigenen Venice-Inferenz-API-Schlüssel erstellen kann, indem er eine von Venice ausgestellte Schlüsselanfrage mit einer Wallet signiert, die gestaktes VVV auf Base hält.
---

Ein KI-Agent, der eine Wallet auf Base kontrolliert, kann seinen eigenen Venice-Inferenz-API-Schlüssel ohne menschliches Zutun erstellen. Der Agent erwirbt VVV, staked es, fordert eine kurzlebige Schlüsselanfrage für seine Wallet an, signiert die lesbare Nachricht der Anfrage und sendet die Signatur zurück, um einen frischen API-Schlüssel zu erhalten, der an die Staking-Wallet gebunden ist. Mit demselben Ablauf lässt sich auch ein ADMIN-Schlüssel erstellen, wenn die Wallet eine Nachricht signiert, die den Schlüsseltyp ADMIN nennt.

Dieser Leitfaden führt Sie End-to-End durch den gesamten Ablauf und behandelt die Finanzierungsoptionen, mit denen Sie nach der Schlüsselerstellung tatsächlich für Inferenz bezahlen können.

## Voraussetzungen {#prerequisites}

* Eine EVM-Wallet auf Base, die vom Agenten kontrolliert wird (Private Key in einer Umgebungsvariablen oder einem Secret Manager).
* Ein kleiner Betrag ETH auf Base für Gas (Staking sind zwei Transaktionen: `approve` und dann `stake`).
* Ein beliebiger Nicht-Null-Betrag VVV zum Staken. Der Mint-Endpoint erfordert lediglich, dass die Wallet ein Nicht-Null-sVVV-Guthaben hat, sodass 1 VVV ausreicht, um einen Schlüssel zu erstellen. Siehe [Bezahlung für Inferenz](#paying-for-inference) für die Voraussetzungen, um bezahlte Endpoints tatsächlich aufzurufen.

<Tip>
  Verwenden Sie eine dedizierte Agenten-Wallet statt einer Treasury-Wallet. Der Private Key der Wallet signiert jede Venice-Token-Anfrage, daher sollte der Schaden im Falle einer Kompromittierung möglichst gering sein.
</Tip>

## Schritte {#steps}

<Steps>
  <Step title="VVV erwerben">
    Senden Sie VVV an die Wallet des Agenten oder lassen Sie den Agenten auf einem DEX wie [Aerodrome](https://aerodrome.finance/swap?from=eth\&to=0xacfe6019ed1a7dc6f7b508c02d1b04ec88cc21bf\&chain0=8453\&chain1=8453) oder [Uniswap](https://app.uniswap.org/swap?chain=base\&inputCurrency=NATIVE\&outputCurrency=0xacfe6019ed1a7dc6f7b508c02d1b04ec88cc21bf) tauschen.

    VVV-Token-Vertrag auf Base: `0xacfE6019Ed1A7Dc6f7B508C02d1b04ec88cC21bf`
  </Step>

  <Step title="VVV bei Venice staken">
    Staken Sie das VVV im [Venice Staking Smart Contract](https://basescan.org/address/0x321b7ff75154472b18edb199033ff4d116f340ff#code) unter `0x321b7ff75154472B18EDb199033fF4D116F340Ff`. Das sind zwei Transaktionen:

    1. `approve(spender, amount)` auf dem VVV-Token, wobei `spender` der Staking-Contract ist.
    2. `stake(amount)` auf dem Staking-Contract.

    <Frame as="div">
      <img src="/images/guides/SC-Stake.png" alt="Smart Contract Staking" />
    </Frame>

    Wenn die zweite Transaktion bestätigt ist, sinkt das VVV-Guthaben der Wallet, und ihr sVVV-Guthaben steigt um denselben Betrag. Der Mint-Endpoint liest das sVVV-Guthaben, um zu bestätigen, dass die Wallet gestaked ist.
  </Step>

  <Step title="Eine Schlüsselanfrage für die Wallet anfordern">
    Rufen Sie `GET /api/v1/api_keys/generate_web3_key` mit der Adresse der Staking-Wallet auf. Der Endpoint ist unauthentifiziert.

    ```bash
    curl --request GET \
      --url 'https://api.venice.ai/api/v1/api_keys/generate_web3_key?address=<wallet address>'
    ```

    Der optionale Query-Parameter `apiKeyType` legt den Schlüsseltyp fest, den die Wallet autorisiert: `INFERENCE` (Standard) oder `ADMIN`. Der Typ ist im Token festgelegt und wird in der Nachricht genannt, fordern Sie also den Typ an, den Sie erstellen wollen. Siehe [Einen ADMIN-Schlüssel erstellen](#minting-an-admin-key).

    Die Antwort enthält zwei Felder:

    - `token`, ein von Venice signiertes Token, das an diese Wallet gebunden ist. Es läuft 15 Minuten nach Ausstellung ab, also signieren und übermitteln Sie es deutlich vorher.
    - `message`, der lesbare Text, den die Wallet signiert. Er nennt die Wallet, den Schlüsseltyp (`INFERENCE`, sofern Sie nicht `ADMIN` angefordert haben), den Aussteller, die Chain, eine einmalige Nonce sowie Ausstellungs- und Ablaufzeit:

    ```text
    Venice API key request

    Sign this only if you are creating a Venice inference API key for this wallet. The key spends from this wallet's Venice account.

    Wallet: <wallet address>
    Key type: INFERENCE
    Issued by: api.venice.ai
    Chain ID: 8453
    Nonce: <random hex>
    Issued At: <ISO 8601 time>
    Expiration Time: <ISO 8601 time>
    ```
  </Step>

  <Step title="Die Nachricht mit der Staking-Wallet signieren">
    Signieren Sie den exakten `message`-String mit der Wallet, die das gestakte VVV hält. Dies ist ein standardmäßiger `personal_sign` (EIP-191). Sowohl `ethers.Wallet.signMessage(message)` als auch `account.signMessage({ message })` in `viem` erzeugen die korrekte Signatur. Verändern Sie die Nachricht nicht: Venice rekonstruiert sie aus dem Token, und die Signatur muss exakt zu ihr passen.
  </Step>

  <Step title="Den API-Schlüssel erstellen">
    `POST`en Sie die Adresse, die Signatur und das Token an denselben Endpoint.

    ```bash
    curl --request POST \
      --url https://api.venice.ai/api/v1/api_keys/generate_web3_key \
      --header 'Content-Type: application/json' \
      --data '{
        "address": "<wallet address>",
        "signature": "<signature of message>",
        "token": "<token>",
        "apiKeyType": "INFERENCE",
        "description": "Agent key minted on <date>"
      }'
    ```

    Erforderliche Felder: `address`, `signature`, `token`, `apiKeyType`. `apiKeyType` muss dem Schlüsseltyp entsprechen, der in der signierten Nachricht genannt wird: `INFERENCE` für ein ohne `apiKeyType` angefordertes Token oder `ADMIN` für ein mit `apiKeyType=ADMIN` angefordertes Token.

    Optionale Felder:

    - `description`, `expiresAt`
    - `consumptionLimit` — die Ausgabenobergrenze für diesen Schlüssel, denominiert in `usd` oder `diem` (`vcu` ist veraltet; verwenden Sie stattdessen `diem`)
    - `limitPeriod` — das Zeitfenster, über das die Obergrenze gemessen wird: `EPOCH` (wird jeden UTC-Tag zurückgesetzt), `MONTH` (wird am 1. jedes UTC-Monats zurückgesetzt) oder `LIFETIME` (wird nie zurückgesetzt, die Obergrenze ist also permanent)
    - `modelPrivacy` — welche Modelle der Schlüssel aufrufen darf, nach Privacy-Stufe: `ALL`, `PRIVATE_TEXT` oder `PRIVATE_ONLY`
    - `ipAllowlist` — IPv4- oder IPv6-Adressen und CIDR-Subnetze, die den Schlüssel verwenden dürfen (bis zu 100 Einträge); eine leere Liste erlaubt jede IP-Adresse

    <Warning>
    `limitPeriod` hat den Standardwert `EPOCH`, wenn es weggelassen wird — das heißt, die Obergrenze **wird jeden Tag zurückgesetzt**, statt eine Lebenszeit-Gesamtsumme zu sein. Ein Schlüssel, der mit `consumptionLimit: {"usd": 50}` und ohne `limitPeriod` erstellt wurde, kann $50 pro Tag ausgeben. Setzen Sie für einen unbeaufsichtigten Agenten-Schlüssel explizit `limitPeriod: "LIFETIME"`, damit das Limit eine permanente Obergrenze ist.
    </Warning>

    Bei Erfolg enthält die Antwort den erstellten `apiKey`-String. Speichern Sie ihn im Secret-Store des Agenten und verwenden Sie ihn als normales Bearer-Token (`Authorization: Bearer <key>`).
  </Step>
</Steps>

## End-to-End-Beispiel {#end-to-end-example}

Das folgende Beispiel verwendet eine echte Wallet aus einer Umgebungsvariablen statt einer zufällig generierten. Eine zufällige Wallet hat kein gestaktes VVV, und der Mint wird mit dem Fehler `Wallet 0x… has no staked VVV on Base` abgelehnt.

```typescript
import { ethers } from "ethers"

const wallet = new ethers.Wallet(process.env.WALLET_PRIVATE_KEY!)
const address = wallet.address

const tokenResponse = await fetch(
  `https://api.venice.ai/api/v1/api_keys/generate_web3_key?address=${address}`,
)
const { data: { token, message } } = await tokenResponse.json()

const signature = await wallet.signMessage(message)

const mintResponse = await fetch("https://api.venice.ai/api/v1/api_keys/generate_web3_key", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    address,
    signature,
    token,
    apiKeyType: "INFERENCE",
    description: "Agent key",
    // A permanent $50 ceiling. Without limitPeriod this would reset daily.
    consumptionLimit: { usd: 50 },
    limitPeriod: "LIFETIME",
  }),
})

const result = await mintResponse.json()
if (!mintResponse.ok) {
  throw new Error(`Mint failed: ${result.error}`)
}

console.log("Minted key:", result.data.apiKey)
```

## Einen ADMIN-Schlüssel erstellen {#minting-an-admin-key}

Ein ADMIN-Schlüssel kann andere API-Schlüssel erstellen und löschen sowie die Abrechnung des Venice-Kontos der Wallet lesen, und er gibt Guthaben dieses Kontos aus. Um einen zu erstellen, fordern Sie ein Token mit `apiKeyType=ADMIN` an, signieren seine Nachricht und senden einen `POST` mit `apiKeyType: "ADMIN"`:

```bash
curl --request GET \
  --url 'https://api.venice.ai/api/v1/api_keys/generate_web3_key?address=<wallet address>&apiKeyType=ADMIN'
```

Die zurückgegebene `message` gibt an, dass sie einen ADMIN-Schlüssel erstellt und was dieser Schlüssel kann:

```text
Venice API key request

Sign this only if you are creating a Venice ADMIN API key for this wallet. An ADMIN key can create and delete other API keys and read billing for this wallet's Venice account, and it spends from this wallet's Venice account.

Wallet: <wallet address>
Key type: ADMIN
Issued by: api.venice.ai
Chain ID: 8453
Nonce: <random hex>
Issued At: <ISO 8601 time>
Expiration Time: <ISO 8601 time>
```

Signieren und übermitteln Sie sie wie in den Schritten oben, mit `"apiKeyType": "ADMIN"` im `POST`-Body. Der Schlüsseltyp eines Tokens lässt sich nicht ändern: Ein `INFERENCE`-Token kann keinen ADMIN-Schlüssel erstellen, und ein `ADMIN`-Token keinen INFERENCE-Schlüssel. ADMIN-Schlüssel erfordern die lesbare Nachricht, daher können [Legacy-Tokens](#legacy-tokens) sie nicht erstellen.

<Warning>
  Lassen Sie eine Wallet eine ADMIN-Nachricht nur signieren, wenn der Agent Schlüssel verwalten oder die Abrechnung lesen muss. Wer den ADMIN-Schlüssel besitzt, kann neue Schlüssel für das Konto erstellen. Bewahren Sie ihn daher mindestens so sorgfältig auf wie den Private Key der Wallet.
</Warning>

## Fehlerreferenz {#error-reference}

Der Endpoint gibt spezifische, umsetzbare Fehlermeldungen zurück. Mappen Sie diese im Agenten, damit er entscheiden kann, ob er es erneut versucht, ein neues Token anfordert oder abbricht.

| Status | Fehlermeldung enthält | Bedeutung | Vorgehen |
| --- | --- | --- | --- |
| `400` | `Invalid wallet address` | Der `address`-Query-Parameter oder das `address`-Feld ist keine gültige EVM-Adresse. | Adresse korrigieren und erneut einreichen. |
| `400` | `Invalid "apiKeyType"` | Der Query-Parameter `apiKeyType` ist weder `INFERENCE` noch `ADMIN`. | Verwenden Sie `INFERENCE` oder `ADMIN`. |
| `400` | `ADMIN keys require a readable key request` | Der `GET` hat `apiKeyType=ADMIN` ohne `?address=` angefordert. | Fordern Sie das Token sowohl mit `address` als auch mit `apiKeyType=ADMIN` an. |
| `400` | `This token was issued for an` | `apiKeyType` im `POST`-Body weicht vom Schlüsseltyp ab, der in der signierten Nachricht genannt wird. | Senden Sie den Typ, für den das Token ausgestellt wurde, oder fordern Sie ein neues Token mit dem gewünschten `apiKeyType` an. Die Fehlermeldung nennt den richtigen `GET`. |
| `400` | `ADMIN keys cannot be created with a token that has no wallet address` | Ein Legacy-Token (ohne `?address=` angefordert) wurde mit `apiKeyType: "ADMIN"` verwendet. | Fordern Sie ein Token mit `?address=<wallet>&apiKeyType=ADMIN` an und signieren Sie seine `message`. |
| `400` | `issued for a different wallet` | Das Token wurde für eine andere `address` angefordert als die im `POST`-Body. | Fordern Sie ein Token an, bei dem `?address=` auf die signierende Wallet gesetzt ist. |
| `400` | `JWT has expired` | Das Validierungs-Token ist abgelaufen, bevor Sie es signiert und eingereicht haben. | Neues Token anfordern, signieren und sofort einreichen. |
| `400` | `JWT signature is invalid` | Das Token wurde nicht von Venice signiert (wahrscheinlich manipuliert oder gefälscht). | Immer ein frisches Token vom `GET`-Endpoint verwenden. |
| `400` | `JWT claims are invalid` | Aussteller oder Audience des Tokens entsprechen nicht dem, was Venice erwartet. | Verwenden Sie das unveränderte Token aus dem `GET`-Endpoint. |
| `400` | `JWT is malformed` | Das eingereichte `token` ist kein JWT. | Stellen Sie sicher, dass Sie den exakten `token`-String aus dem `GET`-Endpoint senden. |
| `400` | `Wallet signature does not match` | Die `signature` ist nicht die Signatur der `address`-Wallet über die `message` des Tokens. | Signieren Sie die exakte `message`, die mit dem Token zurückgegeben wurde, mit der Wallet, die `address` besitzt. |
| `400` | `Tokens without a wallet address are no longer accepted` | Das Token wurde ohne `?address=` angefordert. Diese Legacy-Tokens funktionieren ab dem 26. Dezember 2026 nicht mehr. | Fordern Sie ein Token mit `?address=` an und signieren Sie seine `message`. |
| `400` | `Could not verify wallet signature` | Der RPC-Aufruf zur Verifizierung der Signatur ist fehlgeschlagen (transient). | Mit Backoff erneut versuchen. |
| `400` | `has no staked VVV` | Die Wallet hat ein sVVV-Guthaben von Null. Die vollständige Meldung lautet `Wallet 0x… has no staked VVV on Base`, wobei Ihre Wallet-Adresse anstelle von `0x…` steht, gefolgt von einem Link. Prüfen Sie daher auf `has no staked VVV` statt auf den vollständigen Text. | Zuerst VVV staken, dann erneut versuchen. |

## Legacy-Tokens {#legacy-tokens}

Vor November 2026 stellte der Endpoint Tokens ohne Wallet-Adresse aus, und die Wallet signierte den rohen Token-String. Diese Tokens erstellen noch bis **26. Dezember 2026, 00:00 UTC** INFERENCE-Schlüssel, und Antworten darauf enthalten die Header `Deprecation`, `Sunset` und `Link`. Nach diesem Datum lehnt `POST` sie ab. Wechseln Sie vorher zu `?address=` und signieren Sie `message`.

## Bezahlung für Inferenz {#paying-for-inference}

Einen Schlüssel zu erstellen und damit bezahlte Endpoints aufrufen zu können sind zwei verschiedene Dinge. Ein frisch erstellter Schlüssel authentifiziert sich korrekt, kann aber keine bezahlten Endpoints (z. B. `/chat/completions`) aufrufen, bis das Konto der Wallet ein verfügbares Guthaben hat.

Der erstellte Schlüssel kann vom Benutzerkonto in dieser Prioritätsreihenfolge ausgeben: DIEM, dann verdiente Credits, dann gebündelte Credits, dann USD.

| Finanzierungsquelle | Autonom? | Wie |
| --- | --- | --- |
| **DIEM aus VVV-Staking** | Ja | Die tägliche DIEM-Zuteilung der Wallet ist proportional zu ihrem Anteil am Staking-Pool. Das Konto benötigt mindestens 0,1 gestakte DIEM, damit überhaupt DIEM ausgegeben werden können. Größere Stakes verdienen proportional mehr tägliches DIEM, das jede Epoche (00:00 UTC) erneuert wird. |
| **USD über Stripe** | Nein (Browser) | Melden Sie sich auf venice.ai mit derselben Wallet an (Sign-In-With-Ethereum). Das Dashboard findet den vorhandenen Benutzerdatensatz. Credits unter Settings, API hinzufügen. |
| **Coinbase Crypto Subscription** | Nein (Browser) | Gleiche Wallet-Anmeldung, dann über das Dashboard abonnieren. Der Flow leitet für die eigentliche Zahlung zu Coinbase Commerce um, daher kann er nicht aus einem Skript gesteuert werden. |
| **Coinbase Onramp** | Nein (Browser) | Gleiche Wallet-Anmeldung, dann das Onramp-Widget im Dashboard verwenden. Wird auf der Coinbase-UI gehostet. |

Wenn der Agent einen vollständig krypto-nativen, headless Finanzierungspfad benötigt, sind die saubersten Optionen:

1. **Mehr VVV staken**, sodass die tägliche DIEM-Zuteilung die Ausgaben des Agenten abdeckt. Der erstellte Schlüssel verwendet dies automatisch.
2. **Verwenden Sie den [x402-Wallet-Flow](/de/guides/integrations/x402-venice-api) anstelle des API-Schlüssels.** Bei x402 signiert der Agent pro Anfrage eine Sign-In-With-X-Nachricht, lädt direkt mit USDC auf Base oder Solana über `POST /api/v1/x402/top-up` auf und bezahlt pro Anfrage. Das x402-USDC-Guthaben ist wallet-gebunden, nicht benutzerbezogen, sodass es nicht als Guthaben für den erstellten Bearer-Schlüssel angezeigt wird, aber es ermöglicht es derselben Wallet, programmatisch für Inferenz zu bezahlen.
