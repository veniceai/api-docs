Les requêtes à l'API Venice sont authentifiées avec des clés API Bearer. Ce guide explique comment créer une clé depuis le tableau de bord Venice, la stocker en toute sécurité et vérifier qu'elle fonctionne.

<Note>
  Si vous développez un agent autonome qui doit générer sa propre clé avec un portefeuille, utilisez plutôt le guide [Création de clé API pour agent autonome](/guides/integrations/generating-api-key-agent).
</Note>

## Avant de commencer {#before-you-start}

* Connectez-vous à votre compte Venice.
* Assurez-vous que le compte dispose d'un solde utilisable avant d'appeler des endpoints payants. Vous pouvez créer une clé avant de financer le compte, mais les requêtes aux modèles n'aboutiront pas tant que le compte ne peut pas consommer de DIEM, de crédits groupés ou d'USD.

<Steps>
  <Step title="Ouvrir les paramètres API">
    Rendez-vous sur [https://venice.ai/settings/api](https://venice.ai/settings/api?utm_source=venice-api-documentation). Vous pouvez également ouvrir cette page depuis l'application Venice en sélectionnant **API** dans vos paramètres.

    Le tableau de bord des paramètres API affiche vos soldes, votre niveau d'API, votre utilisation et vos clés API existantes.
  </Step>

  <Step title="Démarrer la création d'une nouvelle clé">
    Sélectionnez **Generate New API Key**, puis configurez la clé :

    * **Description :** utilisez un nom court qui identifie l'application, l'environnement ou l'intégration qui utilisera cette clé.
    * **API Key Type :** utilisez **Inference Only** pour les requêtes normales aux modèles. Utilisez **Admin** uniquement lorsque la clé doit gérer les clés API de manière programmatique.
    * **Expires at :** définissez éventuellement une date d'expiration. Si vous laissez ce champ vide, la clé n'expire pas automatiquement.
    * **Epoch Consumption Limits :** limitez éventuellement le montant en DIEM ou en USD que cette clé peut dépenser pendant une période de 24 heures (epoch). Si vous laissez ce champ vide, la clé peut utiliser le solde disponible du compte, dans la limite des plafonds de votre compte.
  </Step>

  <Step title="Générer et copier la clé">
    Cliquez sur **Generate**. Venice affichera la clé API complète une seule fois.

    <Warning>
      Copiez la clé immédiatement et stockez-la dans un endroit sécurisé. Une fois la boîte de dialogue fermée, Venice n'affiche plus que des métadonnées d'identification telles que la description de la clé et ses derniers caractères. Si vous perdez la valeur secrète, supprimez la clé et créez-en une nouvelle.
    </Warning>

    Collez la clé exactement telle qu'elle a été émise. Utilisez le bouton de copie de la boîte de dialogue plutôt que de sélectionner le texte à la main, afin de ne pas tronquer le premier ou le dernier caractère ni récupérer un saut de ligne final. Lorsqu'un outil demande la clé dans un champ de formulaire, saisissez la clé seule : sans préfixe `Bearer`, sans guillemets autour et sans espaces au début ou à la fin. Comme le tableau de bord n'affiche plus que les derniers caractères une fois la boîte de dialogue fermée, n'essayez jamais de reconstituer une clé perdue en retapant cette valeur masquée.

    Ajoutez la clé à votre environnement local ou à votre gestionnaire de secrets :

    ```bash
    export VENICE_API_KEY=your-api-key-here
    ```
  </Step>

  <Step title="Vérifier la clé">
    Effectuez une requête à faible risque pour confirmer que l'authentification fonctionne. [Obtenir les limites de débit et les soldes d'une clé API](/fr/api-reference/endpoint/api_keys/rate_limits) ne coûte rien et accepte les deux types de clés. Utilisez-le plutôt que `GET /models`, qui renvoie le catalogue des modèles avec ou sans clé et réussit donc même lorsque votre clé est incorrecte :

    ```bash
    curl --request GET \
      --url https://api.venice.ai/api/v1/api_keys/rate_limits \
      --header "Authorization: Bearer $VENICE_API_KEY"
    ```

    Une réponse réussie renvoie votre niveau d'API, vos soldes et vos limites de débit, et `data.accessPermitted` indique si la clé peut utiliser les endpoints d'inférence.

    Une erreur `401` avec `AUTHENTICATION_FAILED` signifie que la clé elle-même a été rejetée. Affichez la valeur stockée et comparez-la aux derniers caractères affichés dans le tableau de bord : les causes habituelles sont une copie partielle, un préfixe `Bearer` ou des guillemets capturés dans la valeur elle-même, ou un espace ou un saut de ligne parasite à l'une des extrémités. Vérifiez également que l'en-tête se compose de `Bearer`, d'un espace, puis de la clé elle-même, par exemple `Authorization: Bearer $VENICE_API_KEY` dans un shell.
  </Step>
</Steps>

<Warning>
  Désactiver les dépenses en USD lors de la création d'une clé API dans l'application Venice fixe votre limite de dépense en USD à zéro pour cette clé API. Les appels à l'API peuvent échouer avec une erreur de solde insuffisant lorsque votre DIEM disponible ou vos crédits groupés ne peuvent pas couvrir la requête, même si votre compte dispose d'un solde en USD.
</Warning>

## Format de la clé {#key-format}

Les nouvelles clés commencent par un préfixe de type suivi de 42 caractères compatibles URL :

| Préfixe | Type de clé |
| --- | --- |
| `VENICE_INFERENCE_KEY_` | Inference Only |
| `VENICE_ADMIN_KEY_` | Admin |

Les clés plus anciennes continuent de fonctionner telles qu'elles ont été émises : certaines utilisent des tirets dans le préfixe (`VENICE-INFERENCE-KEY-`, `VENICE-ADMIN-KEY-`), et les plus anciennes n'ont pas de préfixe.

Utilisez la clé exactement telle qu'elle a été émise. L'API vérifie la chaîne entière : une clé qu'un outil a mise en minuscules, re-ponctuée, privée de son préfixe ou dotée d'un autre préfixe échoue avec `401` et `Authentication failed`. Certaines pages communautaires affirment que les clés Venice commencent par `vapi_`. Ce n'est pas le cas, et ajouter `vapi_` à une clé la rend inutilisable.

Le préfixe identifie le type de clé. Une clé Admin fonctionne aussi sur les endpoints de modèles, car c'est le type le plus large. Une clé Inference Only sur un endpoint d'administration, par exemple pour lister ou créer des clés ou lire le solde, échoue avec `401` et `Admin API key required`. `GET /api_keys/rate_limits` accepte les deux types.

## Résolution des erreurs de limite de dépense {#troubleshooting-spend-limit-errors}

Les limites de dépense par clé sont distinctes du solde de votre compte. Une clé peut être empêchée de dépenser même lorsque votre compte dispose encore de crédits USD financés, de DIEM ou de crédits groupés. Si une requête renvoie une erreur 402 avec l'un de ces codes, la cause est la limite propre à la clé plutôt que le solde du compte :

* `API_KEY_USD_SPEND_LIMIT_EXCEEDED` — la limite de dépense en USD de la clé est fixée à zéro (les dépenses en USD ont été désactivées à la création) ou l'epoch en cours a atteint son plafond en USD.
* `API_KEY_DIEM_SPEND_LIMIT_EXCEEDED` — la clé a atteint son plafond en DIEM pour l'epoch de 24 heures en cours.

Pour vérifier l'état actuel d'une clé, appelez [Obtenir les limites de débit et les soldes d'une clé API](/fr/api-reference/endpoint/api_keys/rate_limits) et inspectez `data.accessPermitted` et `data.balances`. Pour voir les limites configurées de la clé, appelez [Obtenir une clé API](/fr/api-reference/endpoint/api_keys/get) avec une clé Admin et lisez `consumptionLimits`.

Pour résoudre l'erreur, augmentez ou supprimez les Epoch Consumption Limits de la clé sur [venice.ai/settings/api](https://venice.ai/settings/api?utm_source=venice-api-documentation), ou appelez [Mettre à jour une clé API](/fr/api-reference/endpoint/api_keys/update) avec un nouvel objet `consumptionLimit`. Le champ de la requête est au singulier, même si les réponses des clés API renvoient `consumptionLimits`. Les soldes à l'échelle du compte (USD, DIEM et crédits groupés) sont des sources de paiement indépendantes et sont consommés automatiquement selon disponibilité ; vous n'avez pas besoin d'en choisir une au moment de la requête.

Consultez [Codes d'erreur](/api-reference/error-codes) pour la liste complète des réponses liées à la facturation.

## Bonnes pratiques {#best-practices}

* Créez des clés distinctes pour le développement, la préproduction et la production.
* Privilégiez les clés **Inference Only** pour les applications qui appellent uniquement les endpoints de modèles.
* Limitez l'usage des clés **Admin**, en restreignant strictement leur portée et en les stockant uniquement dans des environnements serveur de confiance.
* Ne committez jamais de clés API dans un système de gestion de versions et ne les exposez jamais dans du code côté client.
* Définissez des dates d'expiration et des limites de consommation pour les clés utilisées dans des environnements temporaires, partagés ou à plus haut risque.
* Supprimez les clés inutilisées et faites tourner toute clé susceptible d'avoir été exposée.

## Appels depuis un navigateur {#calling-from-a-browser}

L'API envoie `access-control-allow-origin: *`, un navigateur peut donc l'appeler directement. Mais la clé se retrouve alors dans votre bundle et devient publique. Placez un petit proxy devant et gardez la clé côté serveur.

Un proxy seul ne suffit pas. `access-control-allow-origin` n'authentifie rien : `curl` et les autres serveurs ignorent complètement CORS, et le nom d'hôte du Worker est public. Un proxy qui se contente d'injecter la clé est un robinet ouvert sur votre solde. L'appelant doit lui aussi prouver son identité.

Il existe deux niveaux, et il importe de savoir lequel vous construisez :

- **Un secret partagé** protège les dépenses. Chaque visiteur détient la même valeur : il empêche donc l'utilisation anonyme de votre Worker, mais pas qu'un visiteur le transmette à d'autres. Convient à un prototype.
- **Un jeton par utilisateur** identifie l'appelant. Le navigateur s'authentifie auprès de votre propre backend, qui émet un jeton de courte durée, et le Worker le valide. C'est l'architecture de production.

Les deux exemples ci-dessous gardent la clé Venice côté serveur. Une troisième règle s'applique aux deux : **utilisez une clé inference-only**, car une clé admin acheminée par un proxy public peut appeler `POST /api_keys` et lire le nouveau secret directement dans la réponse relayée.

### Niveau 1 : un secret partagé {#level-1-a-shared-secret}

Le Worker détient la clé Venice et un secret, et rejette tout ce qui ne comporte pas le secret. Gardez le secret hors du navigateur : faites en sorte que votre backend l'ajoute lorsqu'il appelle le Worker, afin que le navigateur ne communique qu'avec votre backend.

```js index.js
// Only the paths you need. Add deliberately: an inference key still reads
// balances through GET /api_keys/rate_limits.
const ALLOWED = new Set(['/chat/completions', '/image/generate']);

export default {
  async fetch(request, env) {
    if (request.method === 'OPTIONS') {
      return new Response(null, { headers: cors() });
    }
    if (!ALLOWED.has(new URL(request.url).pathname)) {
      return json(404, { error: 'Not found' });
    }
    if (request.method !== 'POST') {
      return json(405, { error: 'Method not allowed' });
    }
    if (request.headers.get('x-proxy-key') !== env.PROXY_SECRET) {
      return json(401, { error: 'Proxy secret required' });
    }
    return forward(request, env);
  },
};

async function forward(request, env) {
  const path = new URL(request.url).pathname;
  const upstream = await fetch(`${env.VENICE_BASE_URL}/api/v1${path}`, {
    method: 'POST',
    headers: { 'content-type': 'application/json', authorization: `Bearer ${env.VENICE_API_KEY}` },
    body: await request.text(),
  });
  return new Response(upstream.body, {
    status: upstream.status,
    headers: { ...cors(), 'content-type': upstream.headers.get('content-type') ?? 'application/json' },
  });
}

const cors = () => ({
  'access-control-allow-origin': 'https://your-site.example',
  'access-control-allow-headers': 'content-type,x-proxy-key',
  'access-control-allow-methods': 'POST,OPTIONS',
});

const json = (status, body) =>
  new Response(JSON.stringify(body), { status, headers: { ...cors(), 'content-type': 'application/json' } });
```

```bash Deploy
npx wrangler deploy index.js --name venice-proxy
npx wrangler secret put VENICE_API_KEY      # an inference-only key
npx wrangler secret put PROXY_SECRET        # any long random value
npx wrangler secret put VENICE_BASE_URL     # https://api.venice.ai
```

Appelez-le depuis votre backend, où le secret reste :

```js Server
await fetch('https://venice-proxy.<account>.workers.dev/chat/completions', {
  method: 'POST',
  headers: { 'content-type': 'application/json', 'x-proxy-key': process.env.PROXY_SECRET },
  body: JSON.stringify({ model: 'venice-uncensored-1-2', messages: [{ role: 'user', content: 'Hi' }] }),
});
```

Les chemins sont ajoutés directement, donc `/chat/completions` atteint `/api/v1/chat/completions` en amont. N'incluez pas `/v1` dans l'URL de base des clients OpenAI que vous faites pointer ici.

Un secret partagé reste un identifiant partagé : limitez le débit de la route avec les règles de rate limiting de Cloudflare avant qu'elle ne reçoive du trafic public.

### Niveau 2 : un jeton par utilisateur {#level-2-a-per-user-token}

Lorsque le navigateur doit appeler le Worker directement, placez votre propre authentification devant. Votre backend vérifie la session dont il dispose déjà et signe un jeton de courte durée, et le Worker vérifie ce jeton au lieu d'une valeur partagée. Il réutilise `ALLOWED`, `forward`, `cors` et `json` du Worker de niveau 1 :

```js index.js
export default {
  async fetch(request, env) {
    if (request.method === 'OPTIONS') {
      return new Response(null, { headers: cors() });
    }
    if (!ALLOWED.has(new URL(request.url).pathname) || request.method !== 'POST') {
      return json(404, { error: 'Not found' });
    }
    if (!(await validToken(request.headers.get('authorization')?.replace(/^Bearer /, ''), env))) {
      return json(401, { error: 'Token required' });
    }
    return forward(request, env);
  },
};

// Verify a token issued by your backend: its signature, expiry and subject.
// Any HMAC over `sub.exp` works; this is the shape, not a full implementation.
async function validToken(token, env) {
  if (!token) return false;
  // The payload itself contains a dot, so split on the last one only.
  const cut = token.lastIndexOf('.');
  if (cut < 1) return false;
  const payload = token.slice(0, cut);
  const key = await crypto.subtle.importKey(
    'raw', new TextEncoder().encode(env.PROXY_SIGNING_KEY),
    { name: 'HMAC', hash: 'SHA-256' }, false, ['verify'],
  );
  const ok = await crypto.subtle.verify('HMAC', key, hexToBytes(token.slice(cut + 1)), new TextEncoder().encode(payload));
  return ok && Number(payload.slice(payload.lastIndexOf('.') + 1)) > Date.now();
}

const hexToBytes = (hex) => new Uint8Array(hex.match(/../g).map((b) => parseInt(b, 16)));
```

Émettez le jeton sur le backend après votre propre vérification de session, afin que le Worker ne conserve jamais d'état utilisateur. Vous obtenez ainsi des limites de débit par utilisateur, la révocation et une facturation attribuable.
