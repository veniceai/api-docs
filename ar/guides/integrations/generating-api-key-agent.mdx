يمكن لوكيل ذكاء اصطناعي يتحكم بمحفظة على Base أن يصدر مفتاح Venice API للاستدلال الخاص به دون أي تدخل بشري. يحصل الوكيل على VVV، ويكدّسها (stakes)، ويطلب طلب مفتاح قصير الأمد لمحفظته، ويوقّع الرسالة المقروءة للطلب، ويُرسل التوقيع للحصول على مفتاح API جديد مرتبط بمحفظة الـ staking.

يستعرض هذا الدليل التدفق الكامل من البداية إلى النهاية ويغطي خيارات التمويل لدفع الاستدلال فعليًا بعد إصدار المفتاح.

## المتطلبات {#prerequisites}

* محفظة EVM على Base يتحكم بها الوكيل (مفتاح خاص في متغير بيئة أو مدير أسرار).
* كمية صغيرة من ETH على Base للـ gas (الـ staking يتطلب معاملتين: `approve` ثم `stake`).
* أي كمية غير صفرية من VVV للـ stake. تتطلب endpoint الإصدار فقط أن يكون لدى المحفظة رصيد sVVV غير صفري، لذا VVV واحد يكفي لإصدار مفتاح. راجع [الدفع للاستدلال](#paying-for-inference) لمعرفة ما تحتاجه لاستدعاء endpoints مدفوعة فعليًا.

<Tip>
  استخدم محفظة وكيل مخصصة بدلًا من محفظة الخزينة. يوقّع المفتاح الخاص للمحفظة كل طلب token من Venice، لذا يجب أن يكون نطاق تأثيرها صغيرًا.
</Tip>

## الخطوات {#steps}

<Steps>
  <Step title="احصل على VVV">
    أرسل VVV إلى محفظة الوكيل، أو اجعل الوكيل يقوم بمبادلة على DEX مثل [Aerodrome](https://aerodrome.finance/swap?from=eth\&to=0xacfe6019ed1a7dc6f7b508c02d1b04ec88cc21bf\&chain0=8453\&chain1=8453) أو [Uniswap](https://app.uniswap.org/swap?chain=base\&inputCurrency=NATIVE\&outputCurrency=0xacfe6019ed1a7dc6f7b508c02d1b04ec88cc21bf).

    عقد token VVV على Base: `0xacfE6019Ed1A7Dc6f7B508C02d1b04ec88cC21bf`
  </Step>

  <Step title="قم بـ stake لـ VVV مع Venice">
    قم بـ stake لـ VVV في [Venice Staking Smart Contract](https://basescan.org/address/0x321b7ff75154472b18edb199033ff4d116f340ff#code) عند `0x321b7ff75154472B18EDb199033fF4D116F340Ff`. هذه معاملتان:

    1. `approve(spender, amount)` على token VVV، حيث `spender` هو عقد الـ staking.
    2. `stake(amount)` على عقد الـ staking.

    <Frame as="div">
      <img src="/images/guides/SC-Stake.png" alt="Smart Contract Staking" />
    </Frame>

    عندما تؤكَّد المعاملة الثانية، ينخفض رصيد VVV للمحفظة ويزداد رصيد sVVV الخاص بها بنفس المقدار. تقرأ endpoint الإصدار رصيد sVVV لتأكيد أن المحفظة قد قامت بـ stake.
  </Step>

  <Step title="اطلب طلب مفتاح للمحفظة">
    استدعِ `GET /api/v1/api_keys/generate_web3_key` مع عنوان محفظة الـ staking. الـ endpoint غير مُصادَقة.

    ```bash
    curl --request GET \
      --url 'https://api.venice.ai/api/v1/api_keys/generate_web3_key?address=<wallet address>'
    ```

    تحتوي الاستجابة على حقلين:

    - `token`، وهو token موقّع من Venice ومرتبط بتلك المحفظة. ينتهي بعد 15 دقيقة من إصداره، لذا وقّعه وأرسله قبل ذلك بكثير.
    - `message`، وهو النص المقروء الذي توقّعه المحفظة. يذكر المحفظة ونوع المفتاح (`INFERENCE`) والجهة المُصدِرة والسلسلة وnonce لمرة واحدة ووقتي الإصدار وانتهاء الصلاحية:

    ```text
    Venice API key request

    Sign this only if you are creating a Venice inference API key for this wallet. The key spends from this wallet's Venice account.

    Wallet: <wallet address>
    Key type: INFERENCE
    Issued by: api.venice.ai
    Chain ID: 8453
    Nonce: <random hex>
    Issued At: <ISO 8601 time>
    Expiration Time: <ISO 8601 time>
    ```
  </Step>

  <Step title="وقّع الرسالة بمحفظة الـ staking">
    وقّع سلسلة `message` كما هي تمامًا بالمحفظة التي تحمل VVV المُكدَّس. هذا `personal_sign` قياسي (EIP-191). كلا `ethers.Wallet.signMessage(message)` و `account.signMessage({ message })` في `viem` ينتجان التوقيع الصحيح. لا تعدّل الرسالة: يعيد Venice بناءها من الـ token، ويجب أن يطابقها التوقيع تمامًا.
  </Step>

  <Step title="أصدر مفتاح API">
    `POST` العنوان والتوقيع والـ token إلى نفس الـ endpoint.

    ```bash
    curl --request POST \
      --url https://api.venice.ai/api/v1/api_keys/generate_web3_key \
      --header 'Content-Type: application/json' \
      --data '{
        "address": "<wallet address>",
        "signature": "<signature of message>",
        "token": "<token>",
        "apiKeyType": "INFERENCE",
        "description": "Agent key minted on <date>"
      }'
    ```

    الحقول المطلوبة: `address` و `signature` و `token` و `apiKeyType`. يجب أن تكون قيمة `apiKeyType` هي `INFERENCE`: الإصدار الموقّع بالمحفظة لا يُنشئ مفاتيح ADMIN. أنشئ مفاتيح ADMIN من [إعدادات API](https://venice.ai/settings/api?utm_source=venice-api-documentation).

    الحقول الاختيارية:

    - `description` و `expiresAt`
    - `consumptionLimit` — سقف الإنفاق لهذا المفتاح، بالعملة `usd` أو `diem` (`vcu` مُهمَل؛ استخدم `diem` بدلًا منه)
    - `limitPeriod` — النافذة الزمنية التي يُقاس السقف عبرها: `EPOCH` (يُعاد ضبطه كل يوم UTC)، أو `MONTH` (يُعاد ضبطه في اليوم الأول من كل شهر UTC)، أو `LIFETIME` (لا يُعاد ضبطه أبدًا، فيكون السقف دائمًا)
    - `modelPrivacy` — النماذج التي يمكن للمفتاح استدعاءها، حسب مستوى الخصوصية: `ALL` أو `PRIVATE_TEXT` أو `PRIVATE_ONLY`
    - `ipAllowlist` — عناوين IPv4 أو IPv6 وشبكات CIDR الفرعية المسموح لها باستخدام المفتاح (حتى 100 إدخال)؛ القائمة الفارغة تسمح بأي عنوان IP

    <Warning>
    القيمة الافتراضية لـ `limitPeriod` عند حذفه هي `EPOCH`، ما يعني أن السقف **يُعاد ضبطه كل يوم** بدلًا من أن يكون إجماليًا مدى الحياة. المفتاح المُنشأ بـ `consumptionLimit: {"usd": 50}` بدون `limitPeriod` يمكنه إنفاق 50$ يوميًا. لمفتاح وكيل يعمل دون إشراف، عيّن `limitPeriod: "LIFETIME"` صراحةً ليكون الحد سقفًا دائمًا.
    </Warning>

    عند النجاح، تحتوي الاستجابة على سلسلة `apiKey` المُصدَرة. خزّنها في مخزن أسرار الوكيل واستخدمها كـ Bearer token عادي (`Authorization: Bearer <key>`).
  </Step>
</Steps>

## مثال شامل {#end-to-end-example}

يستخدم المثال أدناه محفظة حقيقية من متغير بيئة بدلًا من محفظة مُولَّدة عشوائيًا. المحفظة العشوائية ليس لديها VVV مُكدَّس وسيتم رفض الإصدار بخطأ `Wallet 0x… has no staked VVV on Base`.

```typescript
import { ethers } from "ethers"

const wallet = new ethers.Wallet(process.env.WALLET_PRIVATE_KEY!)
const address = wallet.address

const tokenResponse = await fetch(
  `https://api.venice.ai/api/v1/api_keys/generate_web3_key?address=${address}`,
)
const { data: { token, message } } = await tokenResponse.json()

const signature = await wallet.signMessage(message)

const mintResponse = await fetch("https://api.venice.ai/api/v1/api_keys/generate_web3_key", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    address,
    signature,
    token,
    apiKeyType: "INFERENCE",
    description: "Agent key",
    // سقف دائم قدره 50$. بدون limitPeriod كان هذا سيُعاد ضبطه يوميًا.
    consumptionLimit: { usd: 50 },
    limitPeriod: "LIFETIME",
  }),
})

const result = await mintResponse.json()
if (!mintResponse.ok) {
  throw new Error(`Mint failed: ${result.error}`)
}

console.log("Minted key:", result.data.apiKey)
```

## مرجع الأخطاء {#error-reference}

تُعيد الـ endpoint رسائل خطأ محددة وقابلة للتنفيذ. عيّن هذه في الوكيل حتى يتمكن من تقرير ما إذا كان سيعيد المحاولة أم يطلب token جديدًا أم يتوقف.

| الحالة | تحتوي رسالة الخطأ | ما يعنيه | ما يجب فعله |
| --- | --- | --- | --- |
| `400` | `Invalid wallet address` | مُعامل الاستعلام أو حقل `address` ليس عنوان EVM صالحًا. | صحّح العنوان وأعد الإرسال. |
| `400` | `creates INFERENCE keys only` | كانت قيمة `apiKeyType` هي `ADMIN`. | اضبط `apiKeyType` على `INFERENCE`، أو أنشئ مفتاح ADMIN من لوحة التحكم. |
| `400` | `issued for a different wallet` | طُلب الـ token لـ `address` مختلف عن الموجود في جسم الـ `POST`. | اطلب token مع ضبط `?address=` على المحفظة التي توقّع. |
| `400` | `JWT has expired` | انتهى صلاحية token التحقق قبل أن توقّعه وترسله. | اطلب token جديدًا، ووقّعه، وأرسله فورًا. |
| `400` | `JWT signature is invalid` | لم يتم توقيع الـ token من قِبَل Venice (على الأرجح تم العبث به أو تلفيقه). | استخدم دائمًا token جديدًا من endpoint `GET`. |
| `400` | `JWT claims are invalid` | مُصدر الـ token أو الجمهور لا يتطابق مع ما تتوقعه Venice. | استخدم الـ token غير المعدَّل المُعاد من endpoint `GET`. |
| `400` | `JWT is malformed` | الـ `token` المُرسَل ليس JWT. | تأكد من أنك ترسل سلسلة الـ `token` بالضبط المُعادة من endpoint `GET`. |
| `400` | `Wallet signature does not match` | الـ `signature` ليس توقيع محفظة `address` على `message` الخاص بالـ token. | وقّع `message` كما أُعيد مع الـ token تمامًا، باستخدام المحفظة التي تملك `address`. |
| `400` | `Tokens without a wallet address are no longer accepted` | طُلب الـ token دون `?address=`. تتوقف هذه الـ tokens القديمة عن العمل في 26 ديسمبر 2026. | اطلب token مع `?address=` ووقّع `message` الخاص به. |
| `400` | `Could not verify wallet signature` | فشل استدعاء RPC للتحقق من التوقيع (مؤقت). | أعد المحاولة مع backoff. |
| `400` | `has no staked VVV` | المحفظة لديها رصيد sVVV صفر. الرسالة الكاملة هي `Wallet 0x… has no staked VVV on Base` مع عنوان محفظتك مكان `0x…`، يليها رابط، لذا طابِق على `has no staked VVV` بدلًا من النص الكامل. | قم بـ stake لـ VVV أولًا، ثم أعد المحاولة. |

## الـ tokens القديمة {#legacy-tokens}

قبل نوفمبر 2026، كانت الـ endpoint تُصدر tokens دون عنوان محفظة، وكانت المحفظة توقّع سلسلة الـ token الخام. لا تزال هذه الـ tokens تُصدر مفاتيح حتى **26 ديسمبر 2026 الساعة 00:00 UTC**، وتحمل الاستجابات الخاصة بها ترويسات `Deprecation` و `Sunset` و `Link`. بعد ذلك التاريخ، يرفضها `POST`. انتقل إلى `?address=` ووقّع `message` قبل ذلك.

## الدفع للاستدلال {#paying-for-inference}

إصدار مفتاح والقدرة على استدعاء endpoints مدفوعة به شيئان منفصلان. المفتاح المُصدَر حديثًا يصادق بشكل صحيح لكنه لا يستطيع استدعاء endpoints مدفوعة (مثل `/chat/completions`) حتى يكون لدى حساب المحفظة رصيد قابل للإنفاق.

يمكن للمفتاح المُصدَر الإنفاق من حساب المستخدم بترتيب الأولوية هذا: DIEM، ثم الاعتمادات المكتسبة، ثم الاعتمادات المُجمَّعة، ثم الدولار الأمريكي.

| مصدر التمويل | مستقل؟ | كيف |
| --- | --- | --- |
| **DIEM من VVV staking** | نعم | حصة DIEM اليومية للمحفظة تتناسب مع حصتها في تجمع الـ staking. يحتاج الحساب إلى 0.1 على الأقل من DIEM المُكدَّسة ليكون أي DIEM قابلًا للإنفاق. الـ stakes الأكبر تكسب DIEM يومية أكثر بشكل متناسب، تُحدَّث كل epoch (00:00 UTC). |
| **USD عبر Stripe** | لا (متصفح) | سجّل الدخول إلى venice.ai بنفس المحفظة (Sign-In-With-Ethereum). تجد اللوحة سجل المستخدم الموجود. أضف اعتمادات في Settings، API. |
| **اشتراك Coinbase crypto** | لا (متصفح) | تسجيل دخول بنفس المحفظة، ثم اشترك عبر اللوحة. يعيد التدفق التوجيه إلى Coinbase Commerce للدفع الفعلي، لذا لا يمكن تشغيله من سكريبت. |
| **Coinbase onramp** | لا (متصفح) | تسجيل دخول بنفس المحفظة، ثم استخدم widget onramp في اللوحة. مُستضاف على واجهة Coinbase. |

إذا احتاج الوكيل إلى مسار تمويل crypto-native بالكامل وبدون رأس، فإن الخيارات الأنظف هي:

1. **قم بـ stake لمزيد من VVV** بحيث تغطي حصة DIEM اليومية إنفاق الوكيل. يلتقط المفتاح المُصدَر هذا تلقائيًا.
2. **استخدم [تدفق محفظة x402](/ar/guides/integrations/x402-venice-api) بدلًا من مفتاح API.** مع x402 يوقّع الوكيل رسالة Sign-In-With-X لكل طلب، ويشحن مباشرة بـ USDC على Base أو Solana عبر `POST /api/v1/x402/top-up`، ويدفع لكل طلب. رصيد x402 USDC مرتبط بالمحفظة وليس بالمستخدم، لذا فهو لا يظهر كرصيد لمفتاح Bearer المُصدَر، لكنه يسمح لنفس المحفظة بدفع الاستدلال برمجيًا.
